# UniQbook architecture

## Stack and scope

UniQbook is an Expo React Native app for university questions, problem reports, announcements, knowledge articles and club activities. The mobile app uses TypeScript and Expo Router. Firebase Authentication establishes identity, Cloud Firestore stores application data and Cloud Functions enforce protected workflows. These are proposed implementation decisions for the approved mobile concept. Confirm the permitted Firebase billing setup before deploying functions.

## Application layers

| Layer | Responsibility |
|---|---|
| Expo Router screens | Home, Submit Request, My Requests, Request Details, Knowledge Base, Clubs and Events, Notifications, Staff Queue, Club Dashboard and Admin Dashboard. Login and registration are additional routes. |
| Feature modules | Form validation, view state, status display, content search and backend calls for each feature. |
| Firebase Authentication | Email and password sign-in. All new sign-ups have student-level access. Authorized server operations provision staff, club and admin access. |
| Cloud Functions | Validate authenticated calls, assign routes, compare similar requests, return role-filtered responses, write replies and create notifications. An email worker processes eligible updates from a server-side outbox. |
| Cloud Firestore | Persist requests, replies, routing rules, content and alerts. Firestore rules allow only explicitly permitted client reads and writes. |

## First navigation milestone

The root stack waits for Firebase Authentication to restore its session. Signed-out users start at Login and can open Registration. Signed-in users start at Home and can use the existing destination routes. Signing out clears access to the signed-in stack, including its back history. My Requests still links to a local sample record.

## Firebase Authentication setup

1. Register a web app in the Firebase project and enable **Email/Password** under **Authentication → Sign-in method**.
2. Copy `.env.example` to `.env.local` in the repository root. Fill in the four values from **Project settings → Your apps → Web app → SDK setup and configuration**. Use the same web app config for Expo Go and web. Restart Expo after changing these values.
3. For development with the Firebase Auth emulator, set `EXPO_PUBLIC_FIREBASE_AUTH_EMULATOR_URL` in `.env.local`. Use the host machine's LAN address for an Expo Go phone and `localhost` for a browser on the host.

The Firebase JS SDK stores the session in AsyncStorage on native and Firebase's browser persistence on web. Expo Router guards use the restored Firebase identity for navigation. Public registration accepts email and password and grants the baseline student experience. It creates a Firebase Auth identity without a role claim or team membership. Trusted backend operations must treat an authenticated user without a provisioned role as a student and enforce authorization for future protected data operations. Provisioning privileged roles and memberships remains a server responsibility.

## Data model

| Collection | Main fields and use |
|---|---|
| profiles/{uid} | Display name, server-managed role, team membership |
| teams/{teamId} | Name, active status and department or club type |
| categories/{categoryId} | Label, active status and destination team |
| requests/{requestId} | Title, description, request type, category, assigned team, status, anonymous flag, timestamps and optional similar-group ID |
| requestOwners/{requestId} | Owner UID. Available to trusted backend code for ownership checks, the student's request list and notification delivery. |
| requests/{requestId}/replies/{replyId} | Author label, reply body and timestamp |
| issueGroups/{groupId} | Assigned team, category, representative request, summary and approximate duplicate count |
| articles/{articleId} | FAQ or verified article, publishing status and approved publisher |
| clubs/{clubId} and events/{eventId} | Club information, announcement or event details and publishing status |
| users/{uid}/notifications/{id} | Request ID, message, created time and read time |
| mailOutbox/{id} | Notification event, delivery state and retry metadata |

## Request lifecycle

1. A signed-in student enters a title, description and type. The app shows a suggested category. The student can choose another category and flag the request as anonymous.
2. A callable function validates the request and derives its destination from the selected category. Requests without an identifiable destination enter an admin triage queue.
3. The backend compares normalized text against recent open requests in the same destination and category. A similar match suggests a group. Staff can review and correct matches. Every student retains an individual request, history and notifications.
4. A student can view their own request. An authorized staff or club officer can open the assigned queue and post a response. An admin can reroute requests and review aggregate counts.
5. The backend applies the permitted status transition and records the reply and in-app notification together. Important status changes are queued for email. Use a stable notification identifier to avoid creating duplicate outbox records on retries.

The normal lifecycle is Submitted, Assigned, In Progress and Resolved. Automatic routing may take an accepted request directly to Assigned. Store verified routing and role decisions on the server.

## Access decisions

- Route guards handle mobile navigation. The backend checks actual role, ownership and assigned team for every protected call.
- Keep the identity record separate from the ticket. Return a staff-safe view for anonymous tickets and keep ownership fields out of analytics, reply payloads and work queues. The form should tell students to keep identifying details out of anonymous report text.
- Restrict knowledge publishing to authorized roles and scope club publishing to the matching club. Permit users to read and mark only their own notifications.
- Start with deterministic keyword routing and token-based similarity. Describe these accurately in the report. Measure suggestions against prepared examples before choosing a similarity threshold.
- Use test accounts and synthetic content for demos. Validate the required flow once in a real Firebase cloud project and once on a physical device or emulator.

## First integration test

Use two student accounts and staff accounts in two teams. Student A creates an anonymous IT/LMS request. The assigned staff account can view and reply while Student B and the other team cannot open it. Student A can see the reply and in-app notification. The staff response contains no student identity. Then verify that a close match can be grouped while both students keep their own tickets.
